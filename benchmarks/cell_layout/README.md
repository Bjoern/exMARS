# Packed cell experiment (2026-10-20)

The measured machine reports **Apple M1, MacBook Air (MacBookAir10,1), 16 GB**.
These are fresh local measurements, not converted Athlon or historical results.
Compiler: Apple Clang 21.0.0, native arm64, `-std=gnu17 -O3 -fomit-frame-pointer`.

**Conclusion:** retain the current 6-byte cell as the default. The 64-bit prototype
has a modest gain on the small P-space sample, essentially no gain on the 94nop
sample with default early stopping, and a substantial regression on the synthetic
nano sample. The 32-bit prototype also regresses on that nano sample. This is an
initial screening experiment, not a claim that every possible packed layout or
compiler would have the same performance.

## Measurements

Baseline is the **current optimized engine** (commit recorded in `results.json`),
including queue caching, MOV.I shortcuts and, in early mode, both early-exit
proofs. The only production change is a death-table allocation repair, applied to
all variants: on LP64, `u32_t` is actually an 8-byte `unsigned long`, but the
allocation previously reserved 4 bytes per entry. AddressSanitizer reproduced the
overflow before the repair; the repaired builds pass ASan and UBSan.

Each table entry is the median of five runs. Relative speed is the median of
paired `baseline time / variant time` ratios: above 1 is faster. Because medians
are calculated independently, the displayed times need not divide to exactly the
displayed ratio.

| Workload | Mode | Battles per run | Baseline time | 64-bit time (speed) | 32-bit time (speed) |
|---|---|---:|---:|---:|---:|
| 8 real 94nop warriors, core 8000 | Default early | 1,792 | 632.18 ms | 635.82 ms (0.998×) | — |
| Same | Exact | 1,792 | 638.46 ms | 627.41 ms (1.018×) | — |
| 4 real P-space warriors, core 8000 | Default early | 768 | 411.53 ms | 393.22 ms (1.051×) | — |
| Same | Exact | 768 | 422.32 ms | 403.12 ms (1.049×) | — |
| 6 synthetic nano programs, core 80 | Default early | 402,570 | 400.38 ms | 467.30 ms (0.865×) | 459.54 ms (0.871×) |
| Same | Exact | 132,060 | 390.12 ms | 500.15 ms (0.779×) | 506.85 ms (0.768×) |

The default-mode 64-bit 94nop speed ratios ranged from 0.988× to 1.003×;
the P-space ratios ranged from 1.039× to 1.063×. The former is too small and
inconsistent to treat as a benefit. The nano regressions were present in all five
passes. These ranges describe observed run variation, not confidence intervals.

Only 896 distinct 94nop battles, 192 P-space battles, and 2,130 synthetic nano
battles are used. Each workload repeats unchanged until the baseline takes roughly
0.4 seconds; nano has many repetitions because individual battles are very short.
This does not add tournament coverage. Variant order is shuffled deterministically
within each pass. No other benchmark or compilation was run concurrently with the
recorded timing passes.

All pairings within each sample are included, with both warrior orders and fixed
placements. Core size, process limit and cycle budget stay dynamic in every build;
these measurements do not include fixed-hill specialization. Core/process/cycle
settings are 8000/8000/80000 and 80/80/800. Parsing and allocation are outside the
timed regions. Core clearing, warrior loading, simulation, and a small per-round
outcome hash are timed; end-of-match P-space hashing is outside the timer.
P-space persists across rounds of each ordered matchup and resets between them.

The nano sources are deliberately simple imp, dwarf, paper, scanner, clear, and
arithmetic programs, stored verbatim in `results.json` and regenerated by the
runner. They are **not the historical nanobm07 competitive corpus**. A larger real
nano corpus would be needed before making a general conclusion about nano hills.

## Implementation

`prepare.py` generates isolated source trees under `build/cell-layout/`:

- `baseline`: copied current production sources, with the original 6-byte struct.
- `packed64`: one `uint64_t` word, A in bits 0–15, B in 16–31 and metadata in
  32–47. Eight-byte size/alignment; the upper 16 bits are unused.
- `packed32`: one `uint32_t` word, A in bits 0–7, B in 8–15 and metadata in
  16–31. Four-byte size/alignment; allocation rejects cores larger than 256.

The generated interpreter uses explicit shifts, masks, masked field updates,
and scalar copies for the immediate/direct MOV.I shortcut. Registers retain their
original widths. Increment/decrement operates on an unsigned temporary before
writing back, including wrap at core size 256. Postincrement addressing retains
the original target cell, preserving alias behavior.

An anonymous bitfield union view lets the existing assembler and test fixtures
populate cells without rewriting them. The runtime bridge check rejects an
incompatible bitfield layout. This is experimental C code for the measured ABI,
not a portable serialized cell format or a replacement binding ABI. Only these
generated engines have the new layouts; production defaults are unchanged.

The experiment retains the existing execution structure. More extensive changes,
such as retaining a whole packed instruction in a register across decoding or
rewriting modifier operations to update multiple fields together, are not tested.
The results therefore assess this direct packing implementation, not the maximum
possible performance of a redesigned interpreter.

## Validation and reproduction

```sh
python3 benchmarks/cell_layout/run.py --cpu-label 'your CPU' --output /tmp/cell-results.json
python3 benchmarks/cell_layout/check.py
```

Use `--cc` to select the compiler, `--passes` (minimum 3) or `--target-seconds`
to change measurement duration. The runner refuses to overwrite existing results.
Generated binaries and sources are ignored build artifacts. The runner requires
a POSIX monotonic clock; this is separate from the older Windows benchmark suite.
`check.py` uses `cc` and requires that the runner has generated its sources first.

Validation in the recorded run includes:

- Full-state differential checks: 6,400 one-instruction oracle cases plus 8,064
  opcode/modifier/address-mode cases over two rounds, with 1–4 warriors. Full
  cores are 80, 800, 8000, 8192 and 32768; the small-core counterpart uses 80,
  127, 128, 255 and 256. State hashes exclude padding and include core, queues
  and P-space.
- Existing results, early termination, P-space endgame and wide multiplication
  tests; packed32 omits the large-core multiplication fixture.
- ASan/UBSan full-state runs for baseline and packed64, and small-core runs for
  packed32. Leak detection is disabled for these checks.
- All 12 existing CLI compatibility cases for baseline and packed64, including
  the 55440-cell arithmetic case and shared PINs.
- 65,536 A/B combinations checking the 32-bit union/scalar bridge, and rejection
  of core size 257.
- Matching battle outcome/P-space hashes across layouts for every timing pass;
  separate one-pass checks confirm identical early/exact results in all samples.

Raw measurements, source and warrior hashes, per-pass ratios, compiler identity,
and validation outputs are in [results.json](results.json).
